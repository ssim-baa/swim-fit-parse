# 구축 로그 — 2026년 7월

workout 파이프라인을 Garmin Connect CSV 기반에서 원본 `.FIT` 기반으로
전환하고 파서를 신규 구축한 세션의 기록이다.

두 repo에 걸친 작업이므로 여기에 통합한다.

- `swim-fit-parse` (public) — 파서. 본 문서의 위치
- `portfolio-price-refresh` (private) — `workout_dashboard.py`. 포인터만 둔다

작성 목적은 **결정의 근거를 남기는 것**이다. 무엇을 했는지는 커밋 이력이
답하지만, 왜 다른 안을 기각했는지는 어디에도 남지 않는다. 기각된 안이
나중에 다시 제안될 때 같은 논의를 반복하지 않으려면 그 이유가 필요하다.

### 전환의 핵심

**CSV → .FIT.** CSV는 FIT의 진부분집합이다. CSV에는 `workout_step`,
`record`, `pool_length`가 없어 블록 매핑·`hrr_60`·course 판정이 불가능하다.
FIT은 바이너리라 LLM 컨텍스트에 직접 들어갈 수 없고, 그래서 코드 파싱이
구조적으로 강제된다 — 이것이 오히려 이점이다. 세션 컨텍스트가 실측
14,065B에서 1,393B로 줄었다.

**세션 단위 → 블록 단위.** 비교 모집단이 세션 7건에서 시그니처별 누적
24본으로 늘었다. 같은 `50자유×6@s1:20`을 9세션에 걸쳐 비교할 수 있다.

## 2. 파서 아키텍처

### 결정론적 추출만 하고 판정하지 않는 이유

파서는 개인 상수(연령·체중·기준 기록·게이트 임계)를 반입하지 않는다.
임계값이 코드에 박히면 개정할 때마다 repo 배포가 필요해지고, 파서 버전과
판정 기준이 결합된다. 판정 정본은 Notion L2 `rule` 레코드이며 스크립트는
인터프리터 역할만 한다.

파서가 하는 일은 검출과 **제안**까지다. 적용은 사용자가 명시적으로 인자를
넘길 때만 일어난다.

### F1~F6 검출 규칙

검출 지점이 랩에서 length로 내려갔다. FIT에서 각 active length는 정확히
`pool_length`이므로 **거리는 추정치가 아니라 카운트**다. 따라서 실패 모드는
"거리 오추정"이 아니라 턴 미검출로 인한 length 병합·오생성뿐이다.

구 CSV 시대 규칙에 있던 `[거리 과대검출]`은 **존재하지 않는 실패 모드**였다.
Garmin이 거리를 과대추정하는 일은 일어나지 않는다. 구현할 대상이 없어서
검출 로직이 헤맸고, 이것이 사양 결함으로 판명됐다.

| 플래그 | 조건 | 물리적 근거 |
|---|---|---|
| F1 | strokes < 중앙값 × 0.65 | 분할 아티팩트 — 거리 과대 기록 |
| F2 | strokes ≥1.6× **AND** duration ≥1.6× | 턴 미검출 — length 2개가 1개로 |
| F3 | duration ≥1.4×, strokes 0.75~1.25 | 시간 오염 — **거리는 정확, 병합 금지** |
| F4 | length 영법 ≠ 설계 영법 | 영법 오검출 |
| F5 | 실측 본수 ≠ `repeat_value` | 구조 불일치 |
| F6 | `wkt_step_index` 없음 | 루틴 외 추가 (정보) |

**1차 지표가 시간이 아니라 스트로크인 이유**: 제자리에서 정지했다가
재출발하면 시간은 오염되지만 스트로크는 오염되지 않는다. 시간 기반 판정이
실패하는 바로 그 지점에서 스트로크 기반이 작동한다.

실증: 06-29 `length#21`은 시간 비율 0.95(정상 범위)인데 스트로크 비율은
0.56이었다. 시간 기반이었다면 놓쳤을 건이다.

**F3이 핵심이다.** 구 사양은 이 케이스를 병합 대상으로 오분류할 수 있었다.
정지했지만 턴 오검출이 없으면 거리는 맞다. 병합하면 오히려 데이터가 깨진다.

### 그룹 키와 최소 크기

정규화 기준은 **동일 파일 내 동일 `wkt_step_index` 그룹의 중앙값**이다.

`wkt_step_index`는 파일 내에서만 유일하다. 07-25는 두 파일(웜업 + 스피드)이
각자 `step 2`를 갖는데, 세션 단위로 풀링하면 0.6초 드릴 아티팩트와 실제
50m 자유형이 한 그룹이 되어 중앙값 25.2초라는 무의미한 기준이 나온다.
그 결과 정상 4건이 전부 이상으로 판정됐다.

n<5 그룹은 평가에서 제외하되 **침묵하지 않고 "평가 불가(n=x)"로 출력**한다.
침묵은 "확인했고 정상"으로 읽힌다.

### C1/C2/C3 확정 테스트

F1 후보를 교정 제안으로 승격시키려면 확정 근거가 필요하다.

| 테스트 | 조건 | 커버하는 물리 |
|---|---|---|
| C1 설계 대조 | 초과 length 수 E == 랩 후보 수 | 조각이 **추가**된 경우 |
| C2 합산 복원 | 인접 후보 스트로크 합이 0.75~1.25 복원 | 하나가 **쪼개진** 경우 |
| C3 미확정 | 둘 다 미성립 | 제안 없음 — 문진 대상 |

**C1과 C2는 포함 관계가 아니라 상보 관계다.** 사양 초안은 "C1이 C2를 포함하는
상위 테스트"로 기술했으나 실측이 이를 반증했다.

- **added (07-28)**: 조각 1개가 추가 → 후보 1개, 초과 E=1 → **후보 == E** → C1 성립
- **carved (07-18)**: 1개가 3개로 쪼개짐 → 후보 3개, 초과 E=2 → **후보 == E+1** → C1 불성립, C2가 잡음

carved에서는 후보가 항상 E보다 1 많다. 실제 length 1개가 후보 안에 섞여
있기 때문이다. 두 테스트가 각자의 케이스를 정확히 커버하므로 실용상 공백은
없다.

**혼합 케이스 예비 규칙은 도출했으나 구현하지 않았다.** 후보를 연속 런으로
묶고 런별 제거 수 `max(k−1, 1)`을 합산해 E와 대조하면 두 케이스가 모두
설명된다(런 k=1 → 1, k=3 → 2). 실물 혼합 케이스가 나오기 전까지 만들지
않는다 — 검증할 데이터가 없는 코드는 틀렸는지 알 수 없다. 현재 C3 안전
강하가 공백을 메운다.

### `--drop-lengths`가 `--merge`를 대체한 이유

**검출 단위와 조작 단위가 어긋나 있었다.** 검출은 length에서 하는데 조작은
랩에서 했다. 랩이 최소 단위였던 CSV 시대의 잔재다.

07-18 실증: 올바른 조작은 "랩29와 랩27을 합치기"가 아니라 "랩29의 유령
length 2개 제거"다. 랩을 합치면 정상 150m 본 경계가 사라지고, 기록 거리
단순 합산은 F1이 검출한 오류를 그대로 보존한다(400m vs 실제 300m).

구 처리 규칙의 "거리: 사용자 확인 실거리 기준 재산정"도 폐지했다. 사용자
기억보다 스트로크 증거와 `workout_step.duration_distance` 설계값이 우월하다.
07-18에서 "250m가 아니라 150m"라는 판단은 사용자 기억이 아니라 스트로크
합 66이 인접 랩(66·70)과 일치한다는 사실에서 나왔다.

`--drop-lengths`는 거리를 `잔여 active length 수 × pool_length`로 자동
산출한다. 사람이 거리 숫자를 입력하지 않으므로 입력 오류 클래스가 소멸한다.

**제거가 아니라 흡수다.** 초기 구현은 조각을 버렸는데, 그러면 생존자가
여전히 조각이라 F1이 재발화했다(07-18 실측). 제거된 length의 시간·스트로크는
앞 생존 length로 합산한다 — 실제로 헤엄친 물이기 때문이다.

**독립 수렴 2건**: 07-18과 07-28 모두 교정 후 거리가 사용자가 수동으로
적재했던 L3 값(1500m, 1400m)과 정확히 일치했다. 사람의 판단과 스트로크
증거가 독립적으로 같은 답에 도달했다.

`--merge`는 폐기하지 않고 폴백으로 강등했다. length 교정으로 해소되지 않는
경우에 쓴다. 8세션 실증에서 해당 사례는 0건이다.

### 미구현으로 남긴 것

**F2 교정 수단.** 8세션 corpus에서 발화 0건이고, length 분할은 시간 배분이
추정값이 되어 결정론적이지 않다. 발생하면 그때 GATE 보고 후 결정한다.
미발생 실패 모드에 인프라를 선건축하지 않는다.

**혼합 케이스 규칙.** 위 C1/C2 절 참조.

## 3. 산식 정정 이력

### dps_m 풀 길이 오가정

**무엇이 틀렸나.** v2.9 산식이 25m 풀을 가정했다.
`dps_m = 25 / strokes_per_25m`이었는데 실측 course는 50m다.
기존 7건 전량이 약 4.8배 과소였다(0.48~0.53, 물리적으로 불가능 — 사람은
스트로크당 최소 1m 이상 나아간다).

**어떻게 발견했나.** FIT `session.pool_length`가 선언 필드로 50.0을
반환했다. 추정이 아니라 워치가 기록한 값이다.

**정본.** `dps_m = total_distance / total_cycles`,
`cycles_per_length = total_cycles / num_active_lengths`. 둘 다 원시량에서
직접 산출하며 SWOLF 역산을 쓰지 않는다(반올림 누적 — 07-25 대조 1.7% 괴리).
`strokes_per_25m`은 폐지.

### avg_pace 경과시간 기준

**무엇이 틀렸나.** 분자가 `duration_min`(휴식 포함 경과시간)이었다.
페이스는 수영 지표이므로 분자는 헤엄친 시간이어야 한다.

**어떻게 발견했나.** 사용자가 05-23에서 177 vs 정본 118의 괴리를 지적했다.
v3.2 배치를 설계할 때 이 항목이 누락됐고, 블록 단위 수치는 애초 랩 시간
기준이라 영향이 없어 세션 헤더에만 남아 있었다.

**정본.** 분자 = active length `total_timer_time` 합.
05-23 검산: 2006초 / 17 = 118.0.
`hr_efficiency`는 pace로 나누므로 하류 오염이었다(24.1 → 36.1).
`avg_swolf`도 같은 분자를 쓴다: 2006/34 + 658/34 = 78.4.

회귀에서 7건 중 6건이 기존 L3 적재값과 pace 차 0으로 일치했다. L3가 실제로
active 기준으로 적재돼 있었다는 증거다.

### fade 첫–끝 비교

**무엇이 틀렸나.** `(마지막 − 첫) / 첫`이었다. 양 끝점만 보면 중간을 전부
버리고(n=6에서 4개 무시) 이상치 하나가 결과를 지배한다.

**어떻게 발견했나.** 05-23 `50자유×6` 실측 99·110·109·116·112·119에서
구 산식이 20.2%를 냈다. 사양은 후반부/전반부 평균 비교였고 그 값은 9.1%다.

**정본.** 후반부 평균 / 전반부 평균 − 1. n이 홀수면 중앙 rep은 양쪽에서
제외하고, n<4면 반쪽 평균이 성립하지 않으므로 null.

R02(fade > 10%) 발화가 **6건 → 1건**으로 줄었다. 5건이 오탐이었다.

### total_cycles == 0 블록의 null 처리

**무엇이 틀렸나.** 드릴 블록에서 `cycles_per_length: 0.0`, `swolf: 55`가
나왔다. Garmin은 `swim_stroke='drill'` length에서 스트로크를 세지 않는다.

**어떻게 발견했나.** 05-23 드릴 블록의 swolf 54.95 + 0 = 55가 SWOLF가 아니라
랩타임이라는 것을 사용자가 지적했다.

**정본.** `0`은 "0회 측정"이고 `null`은 "미측정"이다. 서로 다른 사실이다.
`total_cycles == 0`인 블록은 `cycles_per_length`·`swolf`·`dps_m`·`spi`를
전부 null로 방출한다. 0을 넣으면 대시보드 평균이 오염된다.

### rest_median_s vs hrr_rest_s

**무엇이 틀렸나.** 아무것도 틀리지 않았다. 두 값의 정의가 다른데 하나로
읽어 모순처럼 보였을 뿐이다.

**어떻게 발견했나.** 05-23 `100평영·쿨다운`에서 `rest_median_s`가 null인데
`hrr_60`이 38로 채워진 것이 규칙 13 위반으로 의심됐다. 조사 결과 v3.1과
v3.2의 `rest_after()` 함수와 집계부가 바이트 단위로 동일했다 — 산출 방식이
바뀐 적이 없다.

**정본.**

- `rest_median_s` = rep **사이** 휴식의 중앙값. 단일 rep 블록은 null
- `hrr_rest_s` = 블록 **마지막 rep 뒤** 휴식. 게이트가 실제로 평가한 값

05-23 `100평영`은 단일 rep이라 `rest_median_s`는 null이지만 뒤따르는 휴식은
77초라 규칙 13을 충족한다. hrr=38은 정당한 값이었다.

다만 **실제 결함이 하나 있었다**: `hrr_60`이 랩마다 산출되고 `max()`로
집계됐다. 규칙 13은 블록 조건인데 랩 단위로 평가한 뒤 최댓값을 취해, 한
랩이라도 통과하면 블록이 채워졌다. 블록 마지막 rep 단독 평가로 고쳤고,
게이트가 본 휴식 길이를 `hrr_rest_s`로 방출해 감사 가능하게 했다.
회귀 결과 규칙 13 위반 0건.

## 5. 배포 채널 전환

### raw URL + curl이 폐기된 이유

초기 사양은 파서를 GitHub raw URL로 참조하고 세션에서 `curl`로 받아
실행하는 경로였다. **P1 세션이 출처 미검증 원격 스크립트 실행을 거부했고,
그 판단이 옳다.** 공급망 신뢰 경계 문제다.

대안으로 스크립트 전문을 세션에 붙여넣는 방법이 있었으나, 매 세션 약 4K
토큰이 든다. `.FIT` 전환으로 얻은 85% 컨텍스트 절감을 그대로 상쇄한다.

### PyPI로 간 이유

```
pip install swim-fit-parse==3.3
python -m swim_fit_parse <파일...>
```

패키지 매니저는 설치 출처가 명시적이고, 버전이 고정되며, 의존성(`fitparse`)이
자동 해결된다. src 레이아웃 + hatchling 빌드, wheel + sdist 배포.

**provenance 규약**: 출력 1행에 `schema_version` + `parser_tag` 스탬프를
찍는다. P1 자기검증에서 스탬프가 현행 Schema 버전과 다르면 GATE·적재를
중단한다. git 태그는 이동하지 않고 신설한다(v3.1 → v3.2 → v3.3).

### 패키지 존재 판정

**PyPI JSON API 또는 pip로 판정한다. `web_search` 부재는 비존재 근거가
아니다.** 인덱싱 지연으로 오판한 사례가 있었다.

```
https://pypi.org/pypi/swim-fit-parse/json   # 404 = 미존재, 200 = 존재
```

검증은 clean venv에 PyPI에서 설치해서 한다. 로컬 wheel 설치는 배포가
실제로 되었는지를 검증하지 못한다.

### HTML 3섹션

| 섹션 | 답하는 질문 |
|---|---|
| ① 최근 세션 카드 | 이번 세션이 어땠나 |
| ② 성장 레이더 | 초기와 최근이 어떻게 다른가 (방향만) |
| ③ 블록 히트맵 | 같은 블록이 세션에 걸쳐 어떻게 변했나 |

### 등급 모집단 키 — 안 B 채택

등급은 자기 이력 백분위이며 로버스트 z(median·MAD)로 산출한다. 평균·표준편차는
이상치 1건에 끌려간다. 모집단 n<10이면 등급을 억제하고 n만 표기한다 —
결측을 등급으로 위장하지 않는다.

| 대상 | 모집단 키 |
|---|---|
| ① 세션 카드 (pace/SWOLF/dps) | `(course, routine)` |
| ③ 히트맵 블록 지표 | `(course, 시그니처)` |

**안 A(카드도 블록 단위로) 기각 이유**: 카드가 답하는 질문은 "이번 세션이
어땠나"인데 블록 단위로 내리면 "어느 블록을 보여줄 것인가"라는 선택 문제가
새로 생긴다. **대표 블록을 고르는 것 자체가 판정이고, 관찰 축은 판정하지
않는다.** 전부 보여주면 카드가 아니라 표가 된다.

**안 C(카드에 블록 등급 추가) 보류 이유**: 히트맵이 이미 블록 등급을
담당하므로 중복이고, 카드 층위가 흐려지는 비용이 정보량 증가분보다 크다.

**세션 전체를 한 모집단으로 묶었던 초기 구현의 문제**: 초기 3본이
free 2건 + 축소판 1건이고 최근 3본이 스피드 2건 + 축소판 1건이라, dps
2.83 → 2.41 하락이 능력 저하가 아니라 구성 효과였다. 이지 연속 수영은
스트로크가 길고 스프린트 인터벌은 케이던스가 높다.

성장 레이더는 억제하지 않고 **재라벨**했다. 관찰 축(방향 읽기 전용)임을
명시하고, 루틴 구성을 실데이터에서 산출해 병기하며, 구성이 다르면 경고를
띄운다.

### 웜업·쿨다운 모집단 제외

`·웜업`/`·쿨다운` 수식어가 붙은 블록은 비교 모집단에서 제외한다. 규격
세트가 아니라 거리 편차가 크고(실측 250·300·350·400m), 거리가 시그니처
키의 일부라 세션마다 다른 모집단이 생겨 히트맵을 파편화한다.

**별도 섹션으로 분리**했다. 숨기면 적재된 데이터가 사라진 것처럼 보이고,
본 표에 섞으면 비교 모집단이 오염된다. 분리는 둘 다 피한다.

**강도 색은 제거**하고 출현 여부만 `●`로 표시한다. 회색조로 분리하는 안을
기각한 이유: 색을 어떤 형태로든 렌더하면 "어느 쪽이 진한가"를 읽게 되어
비교를 유도한다. 모집단 제외의 취지는 비교하지 않는다는 것이다.

### 히트맵 강도 축

`pace_median`을 **같은 시그니처 내 min~max 상대값으로 정규화**한다. 절대
페이스는 시그니처마다 대역이 달라(50m 스프린트 vs 500m 지구력) 비교가
성립하지 않는다.

### `bm1|` 접두의 이유

```
bm1|[{...},{...}]
```

Notion MCP 커넥터가 텍스트 속성 값을 JSON으로 선파싱하고 **최상위가 배열이면
타입을 거부한다.** 접두 마커가 그 파싱을 깨뜨려 원문 그대로 저장되게 한다.

소비 측은 `value.split("|", 1)[1]`을 `json.loads`에 넘긴다. `bm1`은 페이로드
스키마 버전이며 구조 변경 시 `bm2`로 올린다.

**JSONL은 기각했다** — 블록이 1건이면 단일 행이 그 자체로 유효한 JSON
객체가 되어 같은 거부에 걸린다.

## 9. 경계 규약

**Notion 쓰기는 챗 관리 세션이 독점한다.** Claude Code 세션은 읽기 전용이다.
백필 값 산출까지가 범위이고 적재는 하지 않는다. 위반하면 관리 세션 단일성이
붕괴한다.

**사양 결함을 발견하면 repo에서 고치지 않는다.** 보고하고 정지한 뒤 Schema
개정을 받아 재개한다. 이 세션에서 다음 사양 결함이 이 경로로 처리됐다:

- 랩 단위 페이스 휴리스틱 (CSV 시대 규칙이 FIT 데이터 모델과 불일치)
- `[거리 과대검출]`이 존재하지 않는 실패 모드
- 검출 단위(length)와 조작 단위(lap) 불일치
- "거리: 사용자 확인 실거리 기준 재산정" (증거 위계 역전)
- C1이 C2를 포함한다는 오판 (실측이 상보 관계임을 보임)

**파서 버전 정본은 Notion Workflow preconditions 한 곳이다.** 태그를 올리면
Schema 인계 절 §A와 함께 양쪽을 동기해야 하며, 이는 의무로 명문화됐다.
파서를 올릴 사유가 생기면 태그 push 전에 보고한다.

**cron·확증 축 무접촉.** 스냅샷 게시는 사용자가 Action을 수동 실행한다.

## 회귀 셋 결손 감지 — `tools/regression_coverage.py` (Q-011, 2026-09-04)

L3 세션 목록과 `fitfiles-swim/`을 대조해 결손 .FIT을 드러낸다. **파일을
만들지 않는다** — 결손 .FIT은 사용자만 공급할 수 있으므로 감지·보고까지다.

**패키지에 넣지 않았다.** `pyproject.toml`의 wheel 대상은 `src/swim_fit_parse`
뿐이므로 `tools/`는 배포되지 않는다. 이 도구는 회귀 셋 운영용이지 파서
사용자의 기능이 아니며, 넣으면 릴리스 없이는 못 고친다.

**두 가지가 자명하지 않다.**

- **파일 수를 세션 수로 읽으면 안 된다.** 워치가 한 세션을 전·후로 나눠
  저장해 현재 29파일 = 24세션이다. 그래서 조립 규칙을 다시 구현하지 않고
  `group_sessions()`를 그대로 태운다 — 다시 구현하면 파서와 어긋난다.
- **날짜는 KST로 맞춘다.** `session.start_time`은 UTC이고 L3 `session_date`는
  KST다. 현재 corpus에는 15:00 UTC 이후 세션이 없어 UTC로 비교해도 전건
  일치하지만, 그건 데이터가 우연히 그런 것이지 규칙이 맞는 게 아니다.

검출 경로는 `--hide`로 확인한다(파일을 지우지 않고 스캔에서만 뺀다).
2026-09-04 확인 — 현 상태 결손 0건, 단일 파일 세션 1건 숨김 → 1건 검출,
3파일 세션(07-04) 중 1파일 숨김 → 0건(세션은 남아 있으므로 결손이 아니다).

## v3.5 — 스트로크 신뢰도 표시 `--strokes-unreliable` (Q-004, 2026-09-04)

### 문제 — 검출은 되는데 반영할 경로가 없었다

F1·F3이 "이 length의 스트로크는 못 믿겠다"를 검출해도 그 판정이 데이터에
들어갈 수단이 없었다(2026-08-01 등재). 교정 연산이 `--drop-lengths`와
`--merge` 둘뿐인데 **둘 다 이 상황에 부적합하다** — 거리와 시간은 정확하고
스트로크만 의심스러운데 length를 통째로 버리면 멀쩡한 정보를 파괴한다.

### 기각안 — 스트로크 수 수동 덮어쓰기

**측정값을 저작하는 것이며 이 파서가 일관되게 거부해 온 것이다.** 사람이
숫자를 입력하는 순간 입력 오류 클래스가 되살아난다(`--drop-lengths`가 거리
숫자를 받지 않는 것과 같은 논거).

### 채택 — 값을 고치는 대신 신뢰도를 표시한다

`--strokes-unreliable <idx,...>`는 length에 표시만 세우고 값을 건드리지
않는다. 하류에서 **스트로크 파생 지표 4종**(`avg_swolf` · `dps_m` ·
`cycles_per_length` · `spi`)만 그 length를 빼고 산출하며, 거리·시간·HR
집계는 전량 포함한다.

**시간과 거리도 함께 빠지는 이유** — SWOLF는 length당 (시간 + 스트로크)이라
스트로크만 빼면 남은 length에 없는 시간이 얹히고, `dps_m`은 거리/스트로크라
분모만 줄이면 값이 그만큼 부풀어 오른다. **제외는 모집단 단위여야 한다.**
`distance_m`은 거리 필드이지 스트로크 파생이 아니므로 블록 출력에서 전량을
유지한다.

전량이 표시된 블록은 `total_cycles == 0`이 되어 4종이 **null**로 나간다 —
0은 "0회 측정"이고 null은 "미측정"이라는 기존 규약과 같은 자리다.

### 판정 주체 — 파서는 스스로 표시하지 않는다

큐 항목이 남긴 미해결 쟁점이다. **구현에서 자동 적용 경로를 아예 두지 않는
것으로 답한다** — 파서는 인자로 받은 것만 적용하고, 인자가 없으면 v3.4와
동일하게 동작한다. F1·F3은 여전히 검출·제안까지만 하며, 표시를 세우는 것은
사용자 GATE다. 자동 적용하면 정상 관측(실제로 이상했던 스트로크)이 지워진다.

### 회귀

**무플래그 corpus 24세션 전량, 스탬프 줄을 제외하고 v3.4와 바이트 동일.**
계약 버전이 오른 사유는 산식 변경이 아니라 **교정 인터페이스 신설**이다
(Schema 계약 버전 상승 4사유 중 하나). `tests/test_v35.py` 29건으로
미도달 분기를 덮었다 — 실세션은 이 경로를 영원히 실행하지 않는다. 사용자가
인자를 주기 전까지 실행되지 않는 것이 설계 전제이기 때문이다.

## 부록 — 커밋 이력·릴리스 상태

**여기에 복제하지 않는다. 정본은 git과 PyPI다** (Q-013 · 2026-09-04).

```bash
git -C swim-fit-parse log --oneline      # 커밋 이력
git -C swim-fit-parse tag                # 태그 = 계약 버전 릴리스
```

종전 이 절은 두 repo의 커밋 목록과 태그 목록을 손으로 옮겨 적었고, 그
사본이 **닫힌 상태를 열린 것으로 적은 채 남았다** — "v3.4는 브랜치에
커밋만, 태그·배포 승인 대기"로 적혀 있었으나 실제로는 태그와 PyPI 배포까지
끝난 뒤였다. 본문 회귀 절은 갱신됐고 부록만 뒤처졌다.

**같은 사실을 두 곳에 적는 구조가 드리프트의 원인이므로 목록을 버리고
조회 경로만 남긴다.** 버전 숫자를 여기 적지 않는 것도 같은 이유다 —
파서 계약 버전의 미러는 Notion Workflow preconditions 한 곳이고, repo
쪽 사실은 태그가 답한다. **거짓 정보보다 없는 것이 낫다.**

각 릴리스가 **왜** 그 내용이 됐는지는 이 문서 본문이 정본이며, 그것이
git이 답하지 못하는 유일한 부분이다.
